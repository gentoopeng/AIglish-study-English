# Firestoreの読み取り削減と上限時の扱い

Firestoreの読み取りは画面を開いた回数ではなく、主に取得したドキュメントの件数で数える。一覧の全件取得・トランザクション内の参照・管理コンソールでの閲覧も使用量に影響する。画像のバイト数を減らすだけではドキュメント読取回数は減らない。

確認した主な不要処理は fix.js の旧管理者リセット世代ポーリング。コメントは60秒だが、実際のsetIntervalは900msで、接続中なら1人1時間に約4,000回のshared/app_settings取得を要求し得た。廃止済みの管理機能なので定期取得を削除する。起動時の既存チェックと学習データ保存は変更しない。

ランキング一覧の自動更新は5分ごとにし、5分以内のタブ切替・画面復帰は取得済み結果を再利用する。手動更新は可能。ランキングと勉強時間の内容が前回成功時から変わらなければ同期トランザクションを省略する。失敗した変更は成功済みとして扱わず、次回の同期に残す。

SDKのドキュメント取得・一覧取得・トランザクションでresource-exhausted／quota exceeded／429を受けた時は5分間新しい読取を抑制する。上限解除を確認するため、時間経過後は再試行可能。取得失敗はエラーとして返し、空のSnapshotを作らない。これにより既存の端末保存・表示済み結果を維持するエラー処理を使う。課金プラン、Firebase設定・実データは変更しない。

無料枠は通常1日50,000読取・20,000書込で、日次枠は米国太平洋時間の午前0時にリセットされる。無料プランで超過するとクラウドの取得・同期などが失敗し得る。共有一覧や新しい端末での初回読込まで常に動作する保証はない。保存済みデータを消さず、不要な再試行を抑える対応である。

公式資料: https://firebase.google.com/docs/firestore/quotas

検証: 変更なしの同期省略・変更時の同期・旧監視の反復取得停止・上限時のバックオフ・ローカルのランキング値とプロフィール画面の保持をChromiumとWebKitで確認。実プロジェクトの請求画面・実際の上限到達は操作していない。使用量の減少はマージ・配信後に確認する。

## 表示中のランキングだけを取得

「学習」と「単語バトル」を分けて初回取得し、各グループで5分間キャッシュする。対戦レートでは上位3人の表彰台と、4位以下がいる場合のみ展開できる一覧を表示する。表示していないグループを先読みしない。タブ移動・グループ切替で進行中のfetchを中止し、15秒の期限を設ける。時間がかかる初回読み込み・手動更新では既存のロードクイズを表示する。

Firestore RESTのrunQueryを利用し、20件ごとに必要なフィールドだけをselectする。対戦ではレート、学習ではrankingLearningSummaryV1と表示に必要なプロフィール情報を取得する。lastActiveAtの単一フィールド条件で直近1か月に絞り、取得後にlastLoginAtを確認する。lastLoginAt未記録の旧ユーザーのみlastActiveAtを使い、アプリ起動時の既存heartbeatでlastLoginAtを追加する。月末を補正した日本時間での1か月前を境界にし、未来・不正な日時は対象外とする。

学習の要約は既存の同期トランザクション内で、クラウドと端末の記録をマージした後に作成する。要約未作成のユーザーだけ、batchGetのmaskで旧学習フィールドを追加取得する。旧履歴を削除・リセットしない。フィールド制限そのものは読取件数を減らさず、転送量とJSON解析負荷を減らす。旧ユーザーの要約移行前は追加読み取りが発生する。最近のユーザーに限定すること、グループ別キャッシュ、画面離脱時の中止が読取件数を減らす。RESTの429にも既存の5分バックオフを適用する。

本番のフィールド制限付きクエリは読み取りのみでHTTP 200を確認した。モックしたRESTレスポンスを使い、投影フィールド、ページ取得、古いログインの除外、キャッシュ、ロードクイズの理解度保存、取消・タイムアウト、320px/393pxでの表示をChromium・WebKitで確認する。実機iPhoneのPWAを操作した検証ではない。

## 今日の勉強時間の表彰台

今日の表彰台もRESTのフィールド制限付き取得に変更し、20件ずつ取得する。勉強時間と表示に必要なプロフィール・旧統計フィールドだけを読み取り、単語帳などを含むプロフィール全体のSDK取得と共通の取得待ち行列を避ける。旧形式の勉強時間記録も従来と同じ判定で扱い、今日5分以上のユーザーを対象にする。今日の表彰台には全体ランキングの1か月ログイン条件を追加しない。

成功した結果を同じ日付の間で5分間再利用する。手動更新は即時取得し、日付が変わった場合も再取得する。タブ移動・画面非表示・アカウント変更時に進行中の通信を中止し、意図した中止を取得失敗として表示しない。15秒のタイムアウトや通信失敗では前回の結果を残し、更新ボタンから再試行できる。古い通信の完了が新しい通信の状態を上書きしない。

保存済みの理解度・勉強時間・リセット世代は変更しない。フィールド制限は転送量を削減し、5分の再利用は読取回数を削減する。Chromium・WebKitで今日の表彰台、旧形式、プロフィールJSONのnull、SDK一覧取得を使わないこと、中止後の復帰、通信失敗とタイムアウト後の再試行、端末の学習記録の保持を確認した。実機iPhoneの再現確認はできていない。

## ワークの保存と上限到達

ワーク編集は公開送信より先に端末へ確定する。利用上限・切断による公開失敗は教材IDと変更世代を端末の公開同期待ちキューに残し、オンライン復帰・起動・成功した自動バックアップの後・ワーク管理の手動再試行で送信する。変更中に以前の送信が完了しても、新しい変更世代を消さない。削除済みの教材は再公開せず、進行中の公開は既存の削除処理の待機対象にする。

理解度・履歴・私用メモ・復習設定だけの変更は公開文書を更新しない。公開内容が変更された場合だけ送信を予約する。公開ワーク一覧の成功結果は5分間再利用し、同時の一覧取得も共有する。公開変更・削除の成功でキャッシュを無効化する。上限中に繰り返し公開を試さない。個人のクラウドバックアップは従来の保存と保留マーカーを使う。端末保存、個人バックアップ、公開同期は別の状態である。

この変更でFirebase側の利用枠は解除・増加しない。日次無料枠を超過している場合は枠がリセットされるまでクラウドの送受信が失敗し得る。容量・課金設定、実プロジェクトの使用量は操作していない。Chromium・WebKitで上限時／切断時の端末保存、同期待ちの再起動保持、回復後の一回だけの公開、理解度変更の公開省略、一覧の再利用を検証した。

## アイコン・名前の共通キャッシュ

ユーザー一覧・ランキングで既に取得した名前と画像を、共有メモの投稿者アイコンでも再利用する。メモ専用の取得は共通キャッシュへ集約し、同じユーザーの同時取得も一つにする。キャッシュは5分間有効で、IndexedDBへ保存する公開情報だけの記録は全体で32件までに制限する。メモリ側も32件に制限し、一般のlocalStorageへ画像の複製を追加しない。プロジェクトと閲覧アカウントごとに分け、アカウント切替後の旧応答を適用しない。上限・切断時には既存キャッシュを維持する。

期限切れの画像はavatarUpdatedAtを含む小さいメタデータを確認し、更新日時が変わった場合だけ画像を取り直す。未記録の旧アカウントは画像も取得し、古い画像を永久に固定しない。初回取得は名前・画像・更新日時を一度に読む。プロフィール保存では画像が変わったときだけ画像更新日時を変更し、名前・文字色・フレームだけの変更で画像を再取得させない。変更のない保存では新しい更新世代を作らず送信を省略し、未同期の変更がある場合のみ同期を再試行する。

ユーザー一覧の再利用も5分へ延長し、他の人のプロフィール詳細は5分間・最大3件を再利用する。本人の学習記録は引き続き最新の同期を行う。明示的な一覧更新・管理者操作による無効化・アカウント切替では詳細キャッシュを破棄する。ランキングの新規取得では従来通りプロフィールの画像も受け取るが、その結果が投稿者画像の追加取得を減らす。

メタデータ確認もFirestoreでは文書読取に数える。画像変更時はメタデータと画像の2回となることがあり、フィールド制限だけで読取件数は減らない。5分以内の再利用、同時取得の共有、画面間の共有が読取回数を減らし、更新日時確認は主に画像の転送量を減らす。Firebase側の利用上限は変更しない。Chromium・WebKitでIndexedDBの再起動復元・32件上限・メタデータのみの確認・変更画像だけの取得・変更なし保存・名前変更時の画像更新日時保持を確認した。

## 分割バックアップと共有メモの重複削減

個人バックアップと単語帳の本文パーツは、最大4文書ずつ保護付きトランザクションで送信する。従来はパーツごとに削除済みアカウントかを確認していたため、12パーツなら同じユーザー文書を12回読んでいた。変更後は3回となる。この75%削減はパーツ保存のアカウント確認に限った値であり、アプリ全体の読取が75%減るという意味ではない。グループごとに削除確認をやり直し、権限をキャッシュしない。パーツ全件の完了後にだけメタデータを更新し、途中失敗時は前の完成済みバックアップと端末記録を維持する。書込文書数とバックアップ形式は変更しない。

フレンド欄では一度取得したユーザー一覧からフレンドの名前・画像・活動日時も更新し、その直前に各フレンドを個別取得する旧処理を実行しない。 非アクティブな登録済みフレンドも引き続き対象にする。共有メモの保存・共有解除が成功したら該当トピックだけをキャッシュへ反映する。全メモのキャッシュを破棄して再取得しない。他のトピックの5分期限を延長せず、明示的な無効化と期限切れの取得は維持する。進行中の古い取得が保存後のキャッシュを上書きしない。

理解度とスワイプ数のランキング公開同期は、連続操作を15秒の単位へまとめる。端末への即時記録、5スワイプ単位のバックアップ予約、30秒ごとの同期確認、画面非表示時の同期、手動更新は維持する。リアルタイム対戦の部屋・スコア通知にはこの待機時間を適用しない。プロフィールは起動時にクラウドと一致していれば追加の同期トランザクションを開始せず、再試行のトランザクションでも同一のフィールドを書き直さない。未送信の変更は残して再試行する。

検証には実Firebaseへ書き込まないモックを使う。12パーツの読取12→3、グループ間のアカウント削除による送信停止、個人バックアップの復元と通信失敗後の世代保持、共有メモの保存・共有解除・再表示で一覧取得が1回に留まること、フレンドの追加個別取得が0件であること、変更なしプロフィールの書込0件を確認する。実際の請求画面の削減量は配信後に確認する必要がある。管理コンソールでの閲覧や他のバージョンのアプリが行う読取も同じ利用枠に含まれる。

## 共有メモの本文を開いたときだけ取得

単語一覧は自分のメモを従来通り表示し、他の人のメモは「共有メモあり」のボタンだけを表示する。本文・投稿者アイコンはこのボタンまたはメモ編集欄を開いたときに、その単語の `publicVocabNotes/{topic}/notes` から取得する。他の単語の本文を取得しない。閉じると共有本文を隠し、5分以内の再表示は本文キャッシュを使う。メモの絞り込みの自分→全員→解除は維持する。

存在確認は `shared/vocab_note_presence_v1_0`〜`f` の16文書へ分割した索引を使う。内容はトピックのハッシュ、投稿者ID、有効／取り消しの更新時刻だけで、本文・名前・画像・理解度を含まない。使用中の分割文書だけを小さい目録文書から確認し、空の分割文書は取得しない。通常の確認は目録1件＋使用中の索引文書（最大16件）を取得し、5分間再利用する。複数カードや絞り込みの同時確認は一つの取得へ集約する。目録の確認も読み取りに数えるが、メモ件数に比例する全件取得を通常表示から除去する。

既存メモは初回に索引へ取り込む。旧バージョンのアプリによる追加・削除も拾うため、索引の最終照合から1日経過した場合に旧メモを再照合する。本番REST照合はownerIdとupdatedAtだけをselectし、本文・画像は取得しない。照合も文書の読取に数えるので全件取得が完全にゼロになるわけではない。照合日時はクラウドに共有し、各端末が起動のたびに移行を行う方式ではない。SDKだけのテスト／互換経路はフィールド制限がない。旧バージョンだけから行われた変更の存在表示には、照合まで最大およそ1日の遅れがある。本文を開く際は5分の本文キャッシュを経て最新取得する。

共有保存・共有解除は本文と対応索引を同じトランザクションで更新する。索引の取り消し時刻を保持し、移行中の古い一覧が削除したメモを復活させない。管理者の完全削除も各メモの索引を取り消す。個人のメモは共有処理より先に端末へ保存する。クラウド失敗時は入力と端末記録を維持し、確認していない空一覧で既存メモを上書きしない。削除済みアカウントへの公開を防ぐ既存ガードも同一トランザクションに適用する。

検証: Chromium／WebKitの40単語表示と全員メモ絞り込みで、1つの分割文書を使う教材では存在情報2件、本文取得0回、他人のアイコン取得0回。1単語を開くと当該2メモだけ取得し、閉じて開き直しても追加取得なし。旧メモの移行・日次照合、共有解除と管理者削除、照合中の削除、失敗時の保持、削除済みアカウントの公開停止、旧照合RESTのフィールド制限をモックで確認する。Firebase本番のデータ・設定を操作した検証ではない。
