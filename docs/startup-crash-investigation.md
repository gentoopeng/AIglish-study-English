# 起動直後の停止の調査（2026-10-18）

報告端末は iPhone 17、Safari のホーム画面アプリ。開いた直後に
「問題が繰り返し起きました」と表示される。これは JavaScript の例外メッセージではなく、
画像だけでは WebKit の終了理由（メモリ、描画、その他）を判別できない。
実機の終了ログとそのユーザーの保存データは取得できていない。

## 確認できた負荷と変更

古い統合セーブの `memory.vocabBooks` に本文を持つ教材が多い場合、
`restorePendingSaveMemory` は開いていない教材もすべて
`__manualVocabDrafts` と `textbooksCacheMap` に展開し、さらに
`core_v4_cache_*` / `core_v4_custom_words_*` に複製していた。
教材本文をファイル参照にする最近のセーブでは目立ちにくいが、古いセーブでは残る。

12 冊、各 2,000 語、補足付きの旧形式セーブ（JSON 約 7.9M 文字）で比較：

| Chromium / 起動後 GC 実施 | 変更前 | 変更後 |
| --- | ---: | ---: |
| メモリ上の教材本文キャッシュ | 12 冊 | 1 冊 |
| メモリ上の教材下書き | 12 冊 | 1 冊 |
| JavaScript 使用ヒープ（参考値） | 約 78MB | 約 39MB |

この値は JavaScript の保持メモリであり、ピーク値、画像・GPU・WebKit プロセス全体の
使用量ではない。端末の終了原因そのものを証明するものでもない。

未選択の本文は専用の端末下書きに保存し、開いた時だけ通常ローダーで展開する。
各教材の理解度は従来通り日時と回復記録を比較して復元する。
統合セーブ、教材ファイル、既存のキャッシュ、学習記録は削除しない。
保存時の収集処理は端末下書きも列挙するため、未選択教材も引き続き保存対象になる。

## 検証

`tests/startup-large-save.smoke.cjs` を Chromium と Linux WebKit で実行。
両方で起動、未選択 11 冊の本文と理解度保持、別教材のオフライン表示、
理解度変更後の再起動を確認。WebKit の起動テストは再読み込み 3 回も通過。
WebKit で 2,000 語のカードを 100 回操作する既存テストも実行する。
これらは iPhone 実機のテストではない。

この試験では報告されたレンダラの異常終了そのものは再現していない。
したがって「今回のクラッシュ原因が確定した」「全端末で解消した」とは判断しない。

## 実機での停止箇所の確認

`startup-monitor.js` は IndexedDB の復元より前に起動し、1KB 未満の固定構造で
現在と前回の起動段階を native localStorage に記録する。通信・定期保存は行わない。
学習内容・ID・画像・キーは記録しない。JavaScript 例外を発火しないプロセス終了でも、
最後に記録された段階を次回確認できる。

`startup-diagnostics.html` はアプリ本体、画像、Firebase、IndexedDB を読み込まない
独立したページ。更新反映後に再発した端末では、このページの診断情報をコピーする。
`storage-hydrate` は端末ストレージの全値復元、`full-save-parse` は統合セーブの解析、
`saved-books-restore` は教材と理解度の復元、`ready` は主要な起動処理の完了を示す。
記録が `ready` でも後続の非同期処理や描画の障害は否定できない。
Safari 自体がこのページにも到達できない場合は、実機の Web Inspector や
OS の終了ログでの調査が必要。

## 音声オフでも再現する報告を受けた調査（Version 10.18.21.54）

ユーザーの iPhone 16 では再現せず、別端末では Safari とホーム画面アプリの両方で
再現するとの報告。診断の起動段階は `ready`。音声設定もオフとのこと。
これらだけでは機種、保存データ、描画等のどれが原因かは確定しない。
パーティクルの存在だけを原因とする根拠はないため、この変更で演出や効果音は変更しない。

共通の `LearningData.read` は、理解度の作業用記録と回復用記録が同一でも
両方をJSON解析し、結合後と作業用の全文を再度JSONに変換して比較していた。
通常のカードも最初の10単語もこの読み込みを使用する。

内容が同じ場合は1回の解析だけで、新しい独立したオブジェクトを返す。
異なる場合も、従来の結合関数で選ばれた単語の参照とキー数から変更の有無を判断する。
保存時はJSON変換を1回行い、同じ文字列を従来の順番で回復用と作業用に書く。
日時・リセットの扱い、回復用記録、即時の端末保存、クラウド保存の境界は維持する。
読み込み結果を永続的なメモリキャッシュにしないため、他タブからの書き換えも毎回反映する。

3,000語、各語に補足・履歴を含む約123万文字の記録を60回読むNode検証で、
変更前は解析120回・全文の文字列化120回、変更後は解析60回・文字列化0回。
同じ実行内の所要時間は約1,920ms→272ms（参考値）。実機での測定値や
クラッシュ原因を示す値ではなく、確認できた不要なデータ処理の削減である。

単体テストには、解析回数、戻り値を変更しても記録に影響しないこと、
回復用記録だけ書いたところで中断した場合の明示的リセットの回復、
外部書き換えとアカウント切替を追加。既存の回復・容量超過・バックアップ復元も検証する。

診断には最後のカード操作の固定ラベルと時刻、最後に読んだ理解度の作業用／回復用の
文字数だけを記録する。単語・回答・メモ・IDは含めない。文字数はメモリに保持し、
通常の起動／操作チェックポイントを保存する時に含める。毎回のデータ読み込みでは
診断を書き込まない。次の実機報告で処理段階とデータ量を比較するための情報である。

## 「起動記録なし」の診断自体の不備（Version 10.19.08.38）

ホーム画面アプリで記録が見つからないという追加報告。これだけでは、
古い版・別の保存領域・記録保存失敗を区別できない。
旧monitorはnative localStorageへの保存失敗を黙って無視していたため、
容量上限時にも診断ページが単に「起動記録なし」と表示することを確認した。
ただし、報告端末が実際に容量上限かどうかや、クラッシュの原因は未確定。

診断だけの独立IndexedDB `aiglish-startup-diagnostics` に最大1件の小さな記録を
非同期で残す。アプリの起動は待たせず、学習用のDB・教材・画像は読み込まない。
保存済みの前回記録を確認してから更新し、他タブの新しい記録を古い日時で上書きしない。
localStorage版とIndexedDB版がある時は、診断ページで新しい方を選ぶ。

診断ページに、診断ページ自身の版、native localStorageのアプリ関連キー数、
ログイン印の有無、専用の一時キーによる1KB書き込みの成否、診断DBの利用可否、
対応ブラウザーではアプリ保存用DBの有無を表示する。キー名・ログインID・学習内容は表示しない。
一時キーは検証後に消し、学習データを削除しない。アプリ関連のnativeキーが0件でも、
学習データがIndexedDBにある場合があるため、これだけでデータ消失とは判断しない。

元のPWAと同じ保存領域から移動できるよう、メニューに「起動診断」を追加。
診断URLを別のホーム画面アイコンとして追加したり、LINE等の別ブラウザーで開いたりせず、
普段のアプリアイコンからメニューで移動して記録を確認する。

Chromium / WebKitで、診断キーへのnative書き込みをQuotaExceededErrorにした条件でも
起動段階・操作・データ量を別DBへ保存し、メニュー経由のページで読めることを検証。
再読み込み後の前回操作、最大1件の記録、学習記録と一時キーの後片付け、
空の別コンテキストと区別できる表示を確認する。この修正は診断の不備への対応であり、
クラッシュ自体の解消を証明するものではない。
